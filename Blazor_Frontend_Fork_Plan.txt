BLAZOR FRONTEND FORK PLAN
DesignAutomation.AppCatelog
==================================================

1. OBJECTIVE
==================================================

Fork the existing DesignAutomation.AppCatelog repository and introduce a
new Blazor frontend while preserving the current Vue frontend, Azure
Functions API, MongoDB database, and authentication behavior.

The first milestone is a reversible Blazor App Catalog experience that
reaches feature parity with the highest-value existing Vue workflows.
Product Health Dashboard capabilities will be introduced incrementally
after the Blazor foundation is stable.

==================================================
2. LOCKED ARCHITECTURE DECISIONS
==================================================

Frontend:
- New Blazor Web App
- .NET 10
- Interactive Server rendering
- Blazor is added in parallel with the existing Vue frontend
- Existing Vue client remains in web/ during the migration

Backend:
- Existing Azure Functions isolated worker API remains authoritative
- .NET 10
- Existing api/v1/* contracts are reused
- No ASP.NET Core backend migration
- No new backend host during the initial frontend migration

Database:
- MongoDB remains the permanent database
- Existing MongoDB repositories remain authoritative
- No PostgreSQL migration
- No Entity Framework Core migration

Authentication:
- Preserve the current Ping/JWT/client-header authentication contract
- Do not introduce a second identity system during the frontend migration
- Function keys, tokens, and secrets must not be committed to source control

Charts:
- Chart.js is the required charting library
- All Blazor charts use a reusable Chart.js JavaScript interop wrapper
- C# owns chart data and chart configuration models
- JavaScript is limited to Chart.js instance creation, updates, resizing,
  and disposal
- Chart.js must be version-pinned and loaded locally or through a
  package-managed/static asset rather than an unpinned CDN

Explicitly excluded from the first fork milestone:
- ASP.NET Core migration
- PostgreSQL
- Entity Framework Core
- Hangfire
- CQRS architecture migration
- Azure DevOps synchronization engine
- New authentication platform
- Seed scripts or automated seed execution

5. FRONTEND EXPERIENCE AND DESIGN SYSTEM
==================================================

The Blazor frontend should preserve recognizable App Catalog behavior while
establishing the Product Health Dashboard visual foundation.

Responsive layout:
- Desktop: 12-column grid, 24px gutters, 32px page margins
- Tablet: 8-column grid
- Mobile: 4-column grid
- Maximum content width approximately 1600px
- Use stable dimensions for cards, charts, tables, toolbars, and controls
- Prevent text, labels, and chart content from overlapping or resizing the
  surrounding layout unexpectedly

Spacing scale:
- 4px, 8px, 12px, 16px, 24px, 32px, 48px, 64px

Standard UI components:
- KPI cards
- Health cards
- Metric cards
- Chart cards
- Table cards
- Alert/risk cards
- AI insight cards
- Buttons and icon buttons
- Dialogs
- Forms
- Tables
- Filters
- Toolbars
- Notifications
- Loading, empty, and error states

Themes:
- Light theme
- Dark theme
- Theme preference stored locally for the user
- Theme changes must not break chart colors or contrast

Accessibility target:
- WCAG 2.2 AA
- Keyboard navigation for all workflows
- Visible focus indicators
- Screen-reader labels and meaningful status announcements
- High-contrast-compatible colors
- Appropriate touch target sizes
- Charts must have an accessible summary or equivalent tabular data

Frontend interaction rules:
- Use familiar icons for icon-only actions and provide tooltips
- Use text labels for actions that are not self-evident
- Use segmented controls, toggles, checkboxes, menus, and date inputs for
  the corresponding interaction types
- Keep loading, empty, error, and unauthorized states explicit
- Avoid page-level explanatory text that duplicates visible controls

Deliverable:
The Blazor shell has a responsive, accessible visual system that can support
both migrated App Catalog pages and future dashboard modules.

6. PHASE 2 - TYPED API CLIENT
==================================================

Create a typed API client in the Blazor project. Components must use the
client rather than constructing raw HTTP requests.

The client must centralize:
- API base URL
- API route construction
- Function key header
- Timestamp header
- Authorization header
- Client headers required by the Functions API
- JSON serialization
- API response handling
- 401 and other error handling
- Cancellation and request failure behavior

Mirror the existing response envelope:
- APIResult<T>
- APIResultType

Initial models and DTOs:
- AppHeader
- AppHeaderDTO
- ReadmeData
- ReadmeLink
- ReadmeMember
- RepoDTO
- PoCDTO
- AppUser
- AppNextPreviousDTO
- PingResponse
- User and role models required by the current API

Initial endpoint coverage, based on the existing Vue DataManager:
- GET api/v1/ping
- GET api/v1/menus
- GET api/v1/apps
- GET api/v1/app/{id}
- GET api/v1/apps/{id}
- GET api/v1/pocs
- GET api/v1/repos
- GET api/v1/users
- GET api/v1/github
- GET api/v1/github/{id}
- POST api/v1/app
- PUT api/v1/app
- DELETE api/v1/app/{id}

Deliverable:
The Blazor application can call the existing API through a tested,
strongly typed client layer.

7. PHASE 3 - AUTHENTICATION COMPATIBILITY
==================================================

Inspect and document the existing authentication flow from:
- web/src/js/security.js
- web/src/js/storage.js
- web/src/views/security/
- api/DesignAutomation.AppCatalog/Security/
- api/DesignAutomation.AppCatalog/Extensions/RequestHeaders.cs

Implement a Blazor authentication adapter that preserves the current
contract rather than redesigning authentication.

Requirements:
- Support the existing token callback and token storage behavior
- Send the required bearer token format
- Send required client and timestamp headers
- Route 401 responses to a Blazor login or unauthorized experience
- Handle expired or invalid tokens consistently
- Keep function keys and secrets in local configuration only
- Avoid exposing server-only secrets to browser-visible configuration

Authentication must be validated before protected pages are migrated.

Deliverable:
A Blazor user can authenticate using the existing API-compatible flow and
protected API calls behave consistently with the Vue client.

10. CHART.JS INTEGRATION PLAN
==================================================

Use Chart.js for all dashboard charts.

Suggested Blazor structure:

blazor/
  Components/
    Charts/
      ChartCard.razor
      LineChart.razor
      BarChart.razor
      DoughnutChart.razor
      ChartModels.cs
  wwwroot/
    js/
      chartInterop.js

Chart responsibilities:

C# / Blazor:
- Define chart data models
- Define labels and datasets
- Define chart options
- Control component lifecycle
- Detect parameter/data changes
- Invoke JavaScript interop
- Dispose chart resources when components are removed

JavaScript interop:
- Locate the canvas element
- Create Chart.js instances
- Update existing chart instances
- Resize charts
- Destroy chart instances
- Return useful errors to Blazor when initialization fails

Chart rules:
- Do not create raw Chart.js instances from individual pages
- Do not duplicate chart lifecycle logic across components
- Do not recreate a canvas unnecessarily when only data changed
- Dispose chart instances during component disposal/navigation
- Keep chart configuration serializable and testable
- Use responsive chart sizing
- Provide empty-data and loading states outside the canvas
- Avoid charts that resize the surrounding layout unpredictably

Initial chart types:
- Line chart for trends
- Bar chart for category comparisons
- Doughnut chart for health/status distribution

Future chart types, added only when supported by real data:
- Area chart
- Heatmap
- Timeline
- Sankey
- Radar

The MVP chart set is line, bar, and doughnut. Additional chart types must
not be added solely as visual decoration; each requires a defined metric,
accessible interpretation, and a responsive layout test.

Chart validation:
- Initial chart render
- Data update
- Option update
- Responsive resize
- Navigation away and disposal
- Empty data
- Invalid data
- JavaScript interop failure
- Multiple charts on one page
- Desktop and mobile dimensions
